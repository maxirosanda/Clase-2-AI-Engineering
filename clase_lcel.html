Prompt

Plantilla con variables como {language} y {text}. Es un molde que se completa al ejecutar.

Modelo

El LLM que procesa el prompt. Necesita OPENAI_API_KEY configurada.

Parser

El modelo devuelve un AIMessage con metadata. El parser extrae solo el texto (.content) como str.

Nuestra primera cadena

from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_template(
    "Translate the following text to {language}: {text}")
model  = ChatOpenAI(model="gpt-4o")
parser = StrOutputParser()

chain = prompt | model | parser

response = chain.invoke({"language": "Spanish", "text": "Learning LCEL is powerful."})
print(response)  # Aprender LCEL es poderoso.

chain no viene de ninguna librería: es una variable que creamos nosotros. Instalación: pip install langchain-openai (Python 3.12 funciona perfecto, conviene usar un entorno virtual).

El operador | y la clase Runnable

El | funciona como un pipe de Unix: la salida de cada pieza es la entrada de la siguiente.

De dónde sale invoke

No es de Python. Todas las piezas son clases de LangChain que heredan de Runnable, que define invoke, stream, batch y el comportamiento del |.

Runnable
 ├── ChatPromptTemplate
 ├── ChatOpenAI
 ├── StrOutputParser
 └── RunnableSequence  ← lo que devuelve |

Solo los objetos de LangChain tienen estos métodos: "hola".invoke() da error.

La "a" del principio significa async. También existe batch_as_completed, que entrega cada resultado apenas termina (con el índice de la entrada).

Síncrono vs asíncrono

script simple 
resp = chain.invoke(datos)

Bloquea hasta tener la respuesta. Para una sola llamada es lo ideal.

código async 
async def main():
    resp = await chain.ainvoke(datos)

asyncio.run(main())

await solo funciona dentro de async def (o en Jupyter).

El async se vuelve útil con varias cosas esperando a la vez: un servidor (FastAPI), muchas llamadas en paralelo, apps con interfaz.

Input shaping: modelar la entrada

En vez de "limpiar" los datos afuera, los transformamos dentro de la cadena.

map_chain = (
    {
        "context":  lambda x: "Información secreta sobre " + x["topic"],
        "question": lambda x: x["question"],
    }
    | prompt
    | model
)
map_chain.invoke({"topic": "gatos", "question": "¿Qué comen?"})

Entra {topic, question} y sale {context, question}: justo las variables que pide el prompt.

RunnablePassthrough

Un runnable que deja pasar la entrada sin modificarla (como lambda x: x).

# Pasar la entrada tal cual a una clave
{ "context": lambda x: buscar(x), "question": RunnablePassthrough() }

# assign: conserva el dict y le AGREGA claves
RunnablePassthrough.assign(
    context=lambda x: "Información sobre " + x["topic"])
# {"topic": ..., "question": ..., "context": ...}

RunnableParallel

Ejecuta varias cadenas al mismo tiempo, con la misma entrada, y devuelve un dict.

chain_tecnica    = prompt_tecnico    | model | parser
chain_financiera = prompt_financiero | model | parser

analisis_total = RunnableParallel(tech=chain_tecnica, finance=chain_financiera)

resultado = analisis_total.invoke({"idea": "Drones que entregan pizza"})
# {"tech": "...", "finance": "..."}
{"idea": ...}
→

chain_financiera → "finance"
→
{"tech", "finance"}

El diccionario es un RunnableParallel

funciona

error

# dict no tiene invoke

El dict solo se convierte en RunnableParallel cuando está unido con | a otro runnable. Si querés usarlo solo, el truco es {...} | RunnablePassthrough(), pero RunnableParallel(...) es más claro.

batch vs RunnableParallel

Qué ejecutaEntradas
batch / abatchla misma cadenavarias
RunnableParallelvarias cadenas distintasla misma
inputs = [{"language": "French", "text": "Hello"},
          {"language": "German", "text": "Goodbye"}]

results = chain.batch(inputs, config={"max_concurrency": 5})
# ["Bonjour", "Auf Wiedersehen"]  (mismo orden que inputs)

max_concurrency limita cuántas se procesan a la vez para evitar rate limits de la API.

batch vs abatch

batch (síncrono)

  • Sin await
  • Paraleliza con hilos
  • Ideal para scripts

abatch (asíncrono)

  • Con await
  • Paraleliza con asyncio
  • Ideal dentro de servidores async

Ambos corren en paralelo y, para llamadas a una API, tardan casi lo mismo. La ventaja de abatch es integrarse con código async (batch bloquearía el servidor), no la velocidad.

Hilos: ¿qué son y por qué sirven?

  • Un hilo es una línea de ejecución dentro del programa. Varios hilos avanzan "a la vez".
  • Casi todo el tiempo de una llamada a la API es esperar la red, no usar CPU.
  • Mientras un hilo espera, los otros avanzan: las esperas se superponen, incluso con un solo núcleo.
  • El GIL impide que dos hilos ejecuten código Python a la vez: no sirven para cálculo pesado (ahí va multiprocessing).
Tipo de tarea¿Ayudan los hilos?
Esperar red / APISí
Cálculo pesado de CPUNo (multiprocessing)

Hilos en Python puro

from concurrent.futures import ThreadPoolExecutor
import time

def tarea(n):
    time.sleep(2)          # simula esperar una API
    return n * 10

with ThreadPoolExecutor(max_workers=5) as pool:
    resultados = list(pool.map(tarea, [1, 2, 3, 4, 5]))

print(resultados)          # [10, 20, 30, 40, 50] en ~2 s, no 10 s

Declarativo vs imperativo

Declarativo: el código describe el qué (el flujo), no el cómo (hilos y estados).

declarativo (LCEL) 
chain = prompt | model | parser
chain.batch(inputs)
imperativo (a mano) 
def procesar(e):
    m = prompt.invoke(e)
    r = model.invoke(m)
    return parser.invoke(r)

with ThreadPoolExecutor(5) as pool:
    res = list(pool.map(procesar, inputs))

Analogía: pedir "una pizza de muzzarella" vs explicar cada paso de la cocina. Otro ejemplo: SQL.

El contrato de datos: salidas estructuradas

Cuando un LLM responde en lenguaje natural, el formato puede cambiar de una llamada a otra. Tres riesgos típicos:

formato

Cambia la forma de la respuesta entre una llamada y la siguiente.

claves

Alucina claves JSON que no existen en tu esquema.

tipos

Devuelve el tipo incorrecto: un str donde esperabas un número.

La solución: definir un contrato formal (un esquema) que la salida del modelo está obligada a cumplir.

¿Por qué Pydantic?

Pydantic es la librería de validación de datos estándar en el Python moderno. Integrada con LangChain, define un esquema formal que el modelo tiene que seguir.

ValidaciónQué garantiza
SintácticaEl JSON es íntegro y parseable
EstructuralTodos los campos requeridos están presentes
SemánticaLos valores cumplen reglas de negocio (ej: confianza entre 0 y 1)
class EntityExtraction(BaseModel):
    topic: str = Field(description="Tema principal del texto")
    entities: List[str] = Field(description="Personas, organizaciones, productos o tecnologías")
    sentiment_score: float = Field(ge=0, le=1, description="0 muy negativo, 1 muy positivo")

El método with_structured_output

llm = ChatOpenAI(model="gpt-4o", temperature=0)
structured_llm = llm.with_structured_output(EntityExtraction)

print(type(result))  # EntityExtraction, no AIMessage ni str
  • LangChain abstrae el parseo manual de la salida.
  • Por debajo usa Tool Calling o JSON Mode del proveedor (OpenAI, Anthropic...) para que el modelo "encaje" su respuesta en tu molde.
  • La description de cada campo le dice al modelo qué completar.

Resiliencia: manejo de errores

Un sistema de IA en producción no solo tiene que ser correcto: tiene que ser robusto. Las llamadas a modelos pueden fallar por dos motivos distintos:

Errores transitorios

Caídas de red, latencia alta o límites de tasa (429 Rate Limit). Vale la pena reintentar: probablemente se resuelven solos.

Errores de formato

El modelo respondió pero no pudo seguir el esquema Pydantic (ValidationError). Es un error lógico: reintentar no lo arregla.

Esta distinción (red vs. lógica) define toda la estrategia de recuperación.

Estrategias de recuperación

En lugar de dejar que el sistema falle y le devuelva un error al usuario:

Retries con backoff exponencial

Si falla, esperamos un poco más antes de cada nuevo intento. Evita saturar el servicio y deja que los fallos momentáneos se resuelvan solos.

Fallbacks

Si un modelo (ej: GPT-4o) falla repetidamente, redirigimos la carga a otro modelo, uno más liviano, o a una respuesta predefinida.

resilient_llm = structured_llm.with_retry(stop_after_attempt=3)
llm_with_fallback = resilient_llm.with_fallbacks([gemini_structured])

Errores comunes de arquitectura

confiar ciegamente 
data = json.loads(resp.content)
data["confianza"]  # ¿y si no existe?

Nunca asumas que json.loads va a funcionar. Usá siempre un validador de esquema.

validar 
structured_llm = llm.with_structured_output(
    EntityExtraction)

El esquema valida sintaxis, estructura y reglas de negocio.

reintentar errores permanentes

Si el prompt tiene un error lógico que causa rechazo, reintentar 10 veces solo desperdicia plata y latencia. Diferenciá errores de transporte (red) de errores de lógica.

Solución (1/2): esquema y modelos

class EntityExtraction(BaseModel):
    topic: str = Field(description="Tema principal del texto")
    entities: List[str] = Field(description="Personas, organizaciones, productos o tecnologías mencionadas")
    sentiment_score: float = Field(ge=0, le=1, description="0 es muy negativo, 1 es muy positivo")

# Solo errores "de transporte": un ValidationError NO está acá
TRANSPORT_ERRORS = (APIConnectionError, APITimeoutError, RateLimitError, InternalServerError)

# max_retries=0: el único que reintenta es with_retry (si no, se multiplican los intentos)
llm = ChatOpenAI(model="gpt-4o", temperature=0, max_retries=0)
structured_llm = llm.with_structured_output(EntityExtraction)
resilient_llm = structured_llm.with_retry(
    retry_if_exception_type=TRANSPORT_ERRORS, stop_after_attempt=3)

# Respaldo: Gemini con el MISMO esquema
gemini = ChatGoogleGenerativeAI(model="gemini-2.5-flash", temperature=0)
gemini_structured = gemini.with_structured_output(EntityExtraction)
llm_with_fallback = resilient_llm.with_fallbacks(
    [gemini_structured], exceptions_to_handle=TRANSPORT_ERRORS)

Versión ampliada del ejercicio: además de with_retry, suma un fallback a Gemini. Hay que definir GOOGLE_API_KEY en el .env.

Solución (2/2): cadena y ejecución

prompt = ChatPromptTemplate.from_messages([
    ("system", "Extraé la información estructurada del texto del usuario."),
    ("human", "{input}"),
])
chain = prompt | llm_with_fallback

async def main():
    try:
        result = await chain.ainvoke({"input": sample_text})
        print(result.model_dump_json(indent=2))

    except ValidationError as e:       # el modelo no respetó el esquema
        print("Error de validación:", type(e).__name__)

    except Exception as e:             # fallaron OpenAI Y Gemini, API key inválida, etc.
        print("Fallaron todos los modelos u otro error:", type(e).__name__, "-", e)

asyncio.run(main())
  • Un ValidationError no activa ni el reintento ni el fallback: se propaga al primer except.
  • load_dotenv() va antes de crear los modelos: ellos buscan las claves al construirse.

Resumen

  • Una cadena es prompt | model | parser, y todas las piezas son Runnables.
  • Métodos: invoke, batch, stream y sus versiones async (a...).
  • Dentro de una cadena, un dict es un RunnableParallel y una lambda es un Runnable.
  • Las claves de salida de un paso deben coincidir con las variables del prompt siguiente.
  • batch (hilos) y abatch (asyncio) paralelizan esperas de red.
  • LCEL es declarativo: describís el flujo, LangChain gestiona el resto.
  • with_structured_output + Pydantic: la salida del modelo es un objeto validado, no texto suelto.
  • with_retry solo para errores de transporte; with_fallbacks para pasar a otro modelo.
