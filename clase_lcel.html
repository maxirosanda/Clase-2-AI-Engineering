Los 3 componentes

PromptChatPromptTemplate
→
ModeloChatOpenAI
→
ParserStrOutputParser

Prompt

Plantilla con variables como {language} y {text}. Es un molde que se completa al ejecutar.

Modelo

El LLM que procesa el prompt. Necesita OPENAI_API_KEY configurada.

Parser

El modelo devuelve un AIMessage con metadata. El parser extrae solo el texto (.content) como str.

Nuestra primera cadena

from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_template(
    "Translate the following text to {language}: {text}")
model  = ChatOpenAI(model="gpt-4o")
parser = StrOutputParser()

chain = prompt | model | parser

response = chain.invoke({"language": "Spanish", "text": "Learning LCEL is powerful."})
print(response)  # Aprender LCEL es poderoso.

chain no viene de ninguna librería: es una variable que creamos nosotros. Instalación: pip install langchain-openai (Python 3.12 funciona perfecto, conviene usar un entorno virtual).

El operador | y la clase Runnable

El | funciona como un pipe de Unix: la salida de cada pieza es la entrada de la siguiente.

De dónde sale invoke

No es de Python. Todas las piezas son clases de LangChain que heredan de Runnable, que define invoke, stream, batch y el comportamiento del |.

Runnable
 ├── ChatPromptTemplate
 ├── ChatOpenAI
 ├── StrOutputParser
 └── RunnableSequence  ← lo que devuelve |

Solo los objetos de LangChain tienen estos métodos: "hola".invoke() da error.

Qué viaja por dentro de la cadena

dict{language, text}

p1 = prompt.invoke({"language": "Spanish", "text": "Hello"})  # ChatPromptValue
p2 = model.invoke(p1)                                          # AIMessage
p3 = parser.invoke(p2)                                         # str

Esto es exactamente lo que hace chain.invoke(...) por dentro.

Los métodos de un Runnable

MétodoQué haceModo
invoke()Una entradasíncrono
ainvoke()Versión async de invokeasíncrono
batch()Lista de entradas, en paralelosíncrono
abatch()Versión async de batchasíncrono
stream()Respuesta en fragmentossíncrono
astream()Versión async de streamasíncrono

La "a" del principio significa async. También existe batch_as_completed, que entrega cada resultado apenas termina (con el índice de la entrada).

Síncrono vs asíncrono

script simple 
resp = chain.invoke(datos)

Bloquea hasta tener la respuesta. Para una sola llamada es lo ideal.

código async 
async def main():
    resp = await chain.ainvoke(datos)

asyncio.run(main())

await solo funciona dentro de async def (o en Jupyter).

El async se vuelve útil con varias cosas esperando a la vez: un servidor (FastAPI), muchas llamadas en paralelo, apps con interfaz.

Input shaping: modelar la entrada

En vez de "limpiar" los datos afuera, los transformamos dentro de la cadena.

map_chain = (
    {
        "context":  lambda x: "Información secreta sobre " + x["topic"],
        "question": lambda x: x["question"],
    }
    | prompt
    | model
)
map_chain.invoke({"topic": "gatos", "question": "¿Qué comen?"})

Entra {topic, question} y sale {context, question}: justo las variables que pide el prompt.

RunnableParallel

Ejecuta varias cadenas al mismo tiempo, con la misma entrada, y devuelve un dict.

chain_tecnica    = prompt_tecnico    | model | parser
chain_financiera = prompt_financiero | model | parser

analisis_total = RunnableParallel(tech=chain_tecnica, finance=chain_financiera)

resultado = analisis_total.invoke({"idea": "Drones que entregan pizza"})
# {"tech": "...", "finance": "..."}
{"idea": ...}
→
chain_tecnica → "tech"
chain_financiera → "finance"
→
{"tech", "finance"}

El diccionario es un RunnableParallel

funciona · forma 1 
RunnableParallel(a=x, b=y)

Explícito: se puede usar solo.

funciona · forma 2 
{"a": x, "b": y} | otro_paso

Implícito: el dict unido con |.

error 
d = {"a": x, "b": y}
d.invoke(...)
# dict no tiene invoke

El dict solo se convierte en RunnableParallel cuando está unido con | a otro runnable. Si querés usarlo solo, el truco es {...} | RunnablePassthrough(), pero RunnableParallel(...) es más claro.

batch vs RunnableParallel

Qué ejecutaEntradas
batch / abatchla misma cadenavarias
RunnableParallelvarias cadenas distintasla misma
inputs = [{"language": "French", "text": "Hello"},
          {"language": "German", "text": "Goodbye"}]

results = chain.batch(inputs, config={"max_concurrency": 5})
# ["Bonjour", "Auf Wiedersehen"]  (mismo orden que inputs)

max_concurrency limita cuántas se procesan a la vez para evitar rate limits de la API.

batch vs abatch

batch (síncrono)

  • Sin await
  • Paraleliza con hilos
  • Ideal para scripts

abatch (asíncrono)

  • Con await
  • Paraleliza con asyncio
  • Ideal dentro de servidores async

Ambos corren en paralelo y, para llamadas a una API, tardan casi lo mismo. La ventaja de abatch es integrarse con código async (batch bloquearía el servidor), no la velocidad.

Declarativo vs imperativo

Declarativo: el código describe el qué (el flujo), no el cómo (hilos y estados).

declarativo (LCEL) 
chain = prompt | model | parser
chain.batch(inputs)
imperativo (a mano) 
def procesar(e):
    m = prompt.invoke(e)
    r = model.invoke(m)
    return parser.invoke(r)

with ThreadPoolExecutor(5) as pool:
    res = list(pool.map(procesar, inputs))

Analogía: pedir "una pizza de muzzarella" vs explicar cada paso de la cocina. Otro ejemplo: SQL.

Error 1: mismatch de tipos

falla 
prompt = ..."chiste sobre {topic}"
chain.invoke("gatos")

El prompt espera un dict y recibe un string.

correcto 
chain.invoke({"topic": "gatos"})

La clave coincide con la variable {topic}.

El primer paso es...La entrada debe ser...
Prompt con variablesdict con esas claves
Prompt sin variablescualquier cosa (se ignora)
Modelo directamentestring o lista de mensajes

Error 2: ignorar el output parser

sin parser 
chain = prompt | model
r = chain.invoke({...})
type(r)  # AIMessage
r.upper()  # AttributeError
con parser 
chain = prompt | model | StrOutputParser()
r = chain.invoke({...})
type(r)  # str
r.upper()  # "HOLA"

Terminá tus cadenas de texto con StrOutputParser() para que el resto de la app reciba un str estándar. Solo omitilo si necesitás la metadata (tokens, etc.).

Ejercicio 1: reseñas (paralelo → síntesis)

Código completo · Ejercicio 1 
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnableParallel

model  = ChatOpenAI(model="gpt-4o")  # el LLM
parser = StrOutputParser()  # convierte la respuesta en str

# Datos de entrada: una lista de reseñas (str)
reviews = ["Llegó rápido y funciona perfecto",
           "Se rompió a la semana, pésima calidad",
           "El envío tardó, pero el producto está bien"]

# Cadena 1: clasifica el sentimiento de una reseña
sentiment_chain = (
    ChatPromptTemplate.from_template("...sentimiento...: {review}") | model | parser)
# Cadena 2: extrae el tema principal de la misma reseña
topic_chain = (
    ChatPromptTemplate.from_template("...tema principal...: {review}") | model | parser)

# Paso paralelo: ambas cadenas reciben la MISMA
# reseña y corren a la vez.
# Devuelve un dict: {"sentiment": ..., "topic": ...}
analysis = RunnableParallel(sentiment=sentiment_chain, topic=topic_chain)

# Prompt final: {sentiment} y {topic} coinciden
# con las claves del dict anterior
ticket_prompt = ChatPromptTemplate.from_template(
    "Sentimiento: {sentiment}\nTema: {topic}\nEscribí una línea de ticket...")

# Cadena completa: reseña → (sentimiento ∥ tema)
# → prompt → modelo → texto
full_chain = analysis | ticket_prompt | model | parser

# batch recibe una LISTA de entradas y ejecuta
# full_chain una vez por cada una, en paralelo.
# Cada entrada es un dict con la clave "review"
# (la variable que esperan las cadenas 1 y 2).
inputs = [{"review": r} for r in reviews]

# max_concurrency=5: máximo 5 cadenas a la vez
# (evita rate limits de la API)
tickets = full_chain.batch(inputs, config={"max_concurrency": 5})

# El resultado conserva el orden: tickets[i] corresponde a reviews[i]
for r, t in zip(reviews, tickets):
    print(f"{r}  →  {t}")
review
→
sentimiento ∥ tema
→
{sentiment, topic}
→
ticket

Regla clave: las claves del dict que sale de un paso deben coincidir con las variables del prompt siguiente. Son 3 llamadas al modelo por reseña.

Ejercicio 2: cadena secuencial con lambda

Código completo · Ejercicio 2 
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

model  = ChatOpenAI(model="gpt-4o")  # el LLM
parser = StrOutputParser()  # convierte la respuesta en str

# Paso 1: recibe {producto} y devuelve una descripción (str)
descripcion_chain = (
    ChatPromptTemplate.from_template(
        "Descripción de 2 oraciones para: {producto}")
    | model | parser)

# Paso 2: recibe {descripcion} y devuelve un tweet (str)
tweet_chain = (
    ChatPromptTemplate.from_template(
        "Resumí en un tweet con 1 emoji: {descripcion}")
    | model | parser)

# Unión: el paso 1 entrega un str, pero el paso 2
# espera un dict {"descripcion": ...}.
# La lambda hace de puente: toma el str (desc)
# y lo envuelve en el dict.
full_chain = (descripcion_chain
    | (lambda desc: {"descripcion": desc})
    | tweet_chain)

# Entradas: lista de dicts, con la clave
# "producto" que espera el paso 1
productos = [{"producto": "termo de acero 1L"},
             {"producto": "mochila antirrobo"}]

# batch: ejecuta full_chain completa (los 2 pasos)
# una vez por cada producto, en paralelo
tweets = full_chain.batch(productos)

# El resultado conserva el orden:
# tweets[i] corresponde a productos[i].
# zip recorre ambas listas a la vez, así
# emparejamos cada producto con su tweet.
for p, t in zip(productos, tweets):
    print(f"{p['producto']}: {t}")
  • La lambda convierte el str del paso 1 en el dict que espera el paso 2.
  • 2 productos × 2 pasos = 4 llamadas al modelo.
  • zip es una función integrada de Python: recorre dos listas en paralelo; funciona porque batch mantiene el orden.

El contrato de datos: salidas estructuradas

Cuando un LLM responde en lenguaje natural, el formato puede cambiar de una llamada a otra. Tres riesgos típicos:

formato

Cambia la forma de la respuesta entre una llamada y la siguiente.

claves

Alucina claves JSON que no existen en tu esquema.

tipos

Devuelve el tipo incorrecto: un str donde esperabas un número.

La solución: definir un contrato formal (un esquema) que la salida del modelo está obligada a cumplir.

¿Por qué Pydantic?

Pydantic es la librería de validación de datos estándar en el Python moderno. Integrada con LangChain, define un esquema formal que el modelo tiene que seguir.

ValidaciónQué garantiza
SintácticaEl JSON es íntegro y parseable
EstructuralTodos los campos requeridos están presentes
SemánticaLos valores cumplen reglas de negocio (ej: confianza entre 0 y 1)
class EntityExtraction(BaseModel):
    topic: str = Field(description="Tema principal del texto")
    entities: List[str] = Field(description="Personas, orgs, productos, tecnologías")
    sentiment_score: float = Field(
        ge=0, le=1, description="0 muy negativo, 1 muy positivo")

result = chain.invoke({"input": text})
print(type(result))  # EntityExtraction, no AIMessage ni str
  • LangChain abstrae el parseo manual de la salida.
  • La description de cada campo le dice al modelo qué completar.

Resiliencia: manejo de errores

Un sistema de IA en producción no solo tiene que ser correcto: tiene que ser robusto. Las llamadas a modelos pueden fallar por dos motivos distintos:

Errores transitorios

Caídas de red, latencia alta o límites de tasa (429 Rate Limit). Vale la pena reintentar: probablemente se resuelven solos.

Errores de formato

El modelo respondió pero no pudo seguir el esquema Pydantic (ValidationError). Es un error lógico: reintentar no lo arregla.

Esta distinción (red vs. lógica) define toda la estrategia de recuperación.

Estrategias de recuperación

En lugar de dejar que el sistema falle y le devuelva un error al usuario:

Retries con backoff exponencial

Si falla, esperamos un poco más antes de cada nuevo intento. Evita saturar el servicio y deja que los fallos momentáneos se resuelvan solos.

Fallbacks

Si un modelo (ej: GPT-4o) falla repetidamente, redirigimos la carga a otro modelo, uno más liviano, o a una respuesta predefinida.

resilient_llm = structured_llm.with_retry(stop_after_attempt=3)
llm_with_fallback = resilient_llm.with_fallbacks([gemini_structured])

Solución: código completo

Código completo · Ejercicio 3 
import asyncio
from typing import List
from pydantic import BaseModel, Field, ValidationError
from dotenv import load_dotenv  # lee el .env y carga las claves

# Errores de transporte del SDK de OpenAI (los que conviene
# reintentar o derivar a otro modelo)
from openai import (APIConnectionError, APITimeoutError,
                    RateLimitError, InternalServerError)
from langchain_openai import ChatOpenAI
from langchain_google_genai import ChatGoogleGenerativeAI  # Gemini
from langchain_core.prompts import ChatPromptTemplate

# ANTES de crear los modelos: ellos buscan OPENAI_API_KEY y
# GOOGLE_API_KEY en el entorno al construirse
load_dotenv()

# --- ESQUEMA ---
class EntityExtraction(BaseModel):
    topic: str = Field(description="Tema principal del texto")
    entities: List[str] = Field(
        description="Personas, organizaciones, productos o tecnologías")
    sentiment_score: float = Field(
        ge=0, le=1,  # regla de negocio: entre 0 y 1
        description="0 es muy negativo, 1 es muy positivo")

# Errores "de transporte": deciden cuándo reintentar y cuándo
# pasar a Gemini. Un ValidationError NO está acá, así que nunca
# activa ni el reintento ni el fallback.
TRANSPORT_ERRORS = (APIConnectionError, APITimeoutError,
                    RateLimitError, InternalServerError)

# --- MODELO PRINCIPAL (OpenAI) ---
# max_retries=0: desactiva los reintentos internos del SDK
# (por defecto hace 2) para que el único que reintente sea
# with_retry y no se multipliquen los intentos
llm = ChatOpenAI(model="gpt-4o", temperature=0, max_retries=0)

# Salida estructurada: devuelve un objeto EntityExtraction validado
structured_llm = llm.with_structured_output(EntityExtraction)

# Reintenta solo errores de transporte (hasta 3 intentos, con
# backoff). Un ValidationError es un error lógico: reintentarlo
# solo gasta plata y latencia.
resilient_llm = structured_llm.with_retry(
    retry_if_exception_type=TRANSPORT_ERRORS,
    stop_after_attempt=3)

# --- MODELO DE RESPALDO (Gemini) ---
# Ajustá el modelo al que tengas disponible en tu cuenta
gemini = ChatGoogleGenerativeAI(model="gemini-2.5-flash", temperature=0)

# Mismo esquema: el resultado tiene la misma forma
# sin importar qué modelo responda
gemini_structured = gemini.with_structured_output(EntityExtraction)

# Si gpt-4o sigue fallando con un error de transporte tras los
# 3 intentos, se llama a Gemini. exceptions_to_handle limita el
# fallback a esos errores: un ValidationError se propaga al except.
llm_with_fallback = resilient_llm.with_fallbacks(
    [gemini_structured],
    exceptions_to_handle=TRANSPORT_ERRORS)

# --- PROMPT Y CADENA ---
prompt = ChatPromptTemplate.from_messages([
    ("system", "Extraé la información estructurada del texto del usuario."),
    ("human", "{input}"),
])
chain = prompt | llm_with_fallback  # reintentos + fallback

sample_text = (
    "LangGraph es una librería de LangChain para construir agentes "
    "con estado. Me parece muy útil, aunque la documentación "
    "todavía tiene huecos.")

# --- EJECUCIÓN ---
async def main():
    try:
        result = await chain.ainvoke({"input": sample_text})
        print(result.model_dump_json(indent=2))
    # El modelo respondió pero no respetó el esquema
    except ValidationError as e:
        print("Error de validación:", type(e).__name__)
    # Fallaron OpenAI (con reintentos) Y Gemini, API key inválida, etc.
    except Exception as e:
        print("Fallaron todos los modelos:", type(e).__name__, "-", e)

asyncio.run(main())

Resumen

  • Una cadena es prompt | model | parser, y todas las piezas son Runnables.
  • Métodos: invoke, batch, stream y sus versiones async (a...).
  • Dentro de una cadena, un dict es un RunnableParallel y una lambda es un Runnable.
  • Las claves de salida de un paso deben coincidir con las variables del prompt siguiente.
  • batch (hilos) y abatch (asyncio) paralelizan esperas de red.
  • LCEL es declarativo: describís el flujo, LangChain gestiona el resto.
  • with_structured_output + Pydantic: la salida del modelo es un objeto validado, no texto suelto.
  • with_retry solo para errores de transporte; with_fallbacks para pasar a otro modelo.
